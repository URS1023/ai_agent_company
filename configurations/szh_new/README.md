# szh_new 六类业务工作流配置交付

> 2026-09-10 后续更新：当前工作流已切换到数据源中心的“银皓数据库副本”（`yinhao_database_copy`）。新增对既有 8 台设备实际巡检记录的补接，质量检查仍为单一产品入口。当前配置和验证见 `datasource.json`、`source_switch_verification.json`、`actual_inspection_verification.json`、`yinhao_live_verification.json` 及 [切换与关联说明](../../docs/analysis/szh_new_20260910/银皓数据源切换与实际巡检补接.md)。下文所列旧运行结果保留为迁移前历史，不作为最新修订结果。

配置日期：2026-09-10。六类公共工作流及 32 个设备工作流均采用 **读取值 → 计算值 → 判断值 → 输出结果 → 结束**。判断直接配置于画布上的分支节点。业务用户通过选数据集、字段、计算方式及比较值操作；设备流程选择设备，质检流程按质检单号读取。数据关联已配置完成，无需自行编写 SQL、Python 或 JSONPath。三类质检也已改为通用节点，保留逐项判定、按单据汇总和补充实测输出。

## 当前可以直接使用的内容

- 1 个 szh_new 数据源，限定访问本次业务使用的 19 张表，使用现有加密凭据。
- 6 个公共工作流：来料、过程、成品质检，以及巡检、保养、维修预警。
- 32 台具有明确单设备巡检或保养计划的设备，每台均绑定一个已发布的预警工作流。
- 32 个设备画布直接展开适用的判断步骤，不再包含通用子流程节点；用户无需手工填写设备 JSON 或 SQL。
- 7 台巡检对象配置 73 个检查项和各自的周期；25 台保养设备配置 141 个设备/润滑点要求。只有有实际维修任务的 1#炉出炉机器人B 同时包含维修分支。
- 32 台设备的最新配置均已实际运行，逐行核对结果只属于当前设备，保存 32 份最新预警报告。
- 每次运行通过“读取值”节点读取设备适用计划的当前要求和执行记录。四个已配置数据集只负责读取、关联和选择记录，时间计算及正常/预警/待确认判断均在后续节点中配置。
- 质检工作流保留汇总判定和原始测量输出，包括数值明细、炉前明细、出厂明细和统计明细。

7 台单设备巡检对象：1#主变、2#主变、原料配电室、柴油发电机、直流充电屏、石灰窑配电室、配料站配电室。

公共巡检入口现在只检查上述 7 台已配置对象的具体要求；旧版区域/分类巡检的 1,275 台汇总结果仍在历史中，不能将旧的聚合统计解释为已配置了这些设备的逐项预警。区域和分类巡检需要先确认计划与设备的可靠关联后扩展。公共维修入口保留 13 台有历史维修任务的设备、共 24 条任务；没有因此新建 13 台预警设备。

这是依据现有计划形成的初始配置范围，不表示其他设备永远不需要预警。后续应由有效业务计划或明确选定范围决定。

## 使用方法

### 设备预警

1. 打开 [设备预警](http://192.168.6.16:8011/alerts)，选择本次配置的设备。
2. 设备入口直接打开工作流。保养主线为：开始 → 读取本设备润滑点、周期和时间 → 计算距上次保养天数 → 判断时间/周期是否缺失 → 判断是否超过本点周期 → 输出结果 → 保存预警结果 → 结束。缺值与异常沿不同连线输出，多个结果通过“汇总输出”汇合。
3. 点击测试运行。参考时间已有默认值，无需填写 JSON、SQL 或重新配置设备。
4. 查看本次运行结果，也可以进入 [预警报告](http://192.168.6.16:8011/alerts/reports) 和 [问题列表](http://192.168.6.16:8011/alerts/problems)。
5. 点击任一读取、计算、判断或输出节点，在“上次运行”中查看表格；判断节点分别显示 IF 和 ELSE 的记录。每页 20 条，可翻页和横向滚动。空值显示“未记录”，原始数据放在折叠项中。
6. 公共入口默认检查该数据集的配置范围；可在读取节点选择设备。设备入口已选定本设备，不必复制长标识。

### 不写代码怎样调整流程

| 节点 | 用户配置的内容 | 保养例子 |
| --- | --- | --- |
| 读取值 | 数据源、数据集、设备、要读取的字段 | 选择“润滑点周期要求与实际保养记录”，勾选周期天数、上次完成时间、参考时间 |
| 计算值 | 结果名称、运算、两个字段或固定值 | 结果叫“已过天数”；运算选“日期间隔（天）”；开始选上次完成时间，结束选参考时间 |
| 判断值（条件分支） | 判断字段、比较方式、另一个字段或固定值 | “已过天数”大于“周期数值”，满足走 IF，不满足走 ELSE |
| 输出结果 | 正常、预警或待确认，说明，保留哪些字段 | 输出预警并保留本点的周期、时间、已过天数与说明 |
| 结束 | 接收前面输出 | 保存并查看这次完整结果 |

读取、计算、输出节点之间默认按连线传递记录；批量判断默认逐条分流，不需要循环代码或变量路径。字段选择只列出已连线上游可提供的读取/计算字段。多个条件可通过“全部满足”“任一满足”组合；字段与字段比较也通过下拉框选择。运算支持加减乘除、天/小时间隔、取值、读取单一数值、读取单一数值上/下限、单位及对应关系转换。复杂文字要求不会被随意转换成数字。

读取参数有两种来源：“使用上游同名输入”和“使用固定值”。当前参考时间默认来自开始节点；需要在读取节点固定参考时间时，切换为“使用固定值”再填写，避免开始节点输入覆盖本节点设置。

### 质量检查

1. 打开上表中来料、过程或成品质检链接，或者在工作流列表搜索 `szh_new`。
2. 点击测试运行，质检单号留空检查本类别全部有效单据，也可填写单号精确查询。源库单号重复时返回全部同号记录，并按唯一单据标识分别汇总，不把不同单据合并为一张。无需手工提供检测数据。来料/过程/成品的类别已分别固定，不会被开始节点的其他输入覆盖。
3. 主“结束”输出包含每张单的原始结果、复判结果、必检项数、实测项数、不合格项数、待确认项数及说明。待确认项数包括缺实测和缺判定依据，不应解释为纯粹的漏检数量。
4. “项目实测与逐项结论”保留实测、标准、上下限和逐项结果；必检项目没有实测也会作为待确认行保留。三类分别输出 3,808 / 2,787 / 5,438 行，其中真正的通用数值实测仍为 3,104 / 775 / 0 行，其余为缺项或无项目单据的占位证据。没有制造新测量值。炉前、出厂和统计明细分别保留独立输出，空数组表示该类别没有匹配记录。
5. 当前数值复判结果保存在工作流运行记录中，没有冒充成检测服务新产生的记录，也没有自动写入原库或覆盖原有质检结论。现有专用质检记录列表不会因此自动新增 3,144 张记录。

质检画布中各节点的配置方法：

| 节点 | 用户操作 | 本次已配置内容 |
|---|---|---|
| 读取值 | 选择数据源、数据集、字段和质检单号 | 实测项目及其标准、必检要求；炉前/出厂/统计补充明细 |
| 计算值 | 选择左值、运算、右值，填写结果名称 | 实测减阈值、实测减下界；识别标准文本是否涉及夏季或冬季 |
| 判断值 | 选择字段、比较方式、固定值或另一字段；组合“全部满足/任一满足” | 缺实测、阈值有效性、是否超限；季节条件不明时待确认 |
| 按单据统计 | 勾选分组字段，选择计数/求和及来源字段 | 将每个项目的不合格/待确认标记按单据汇总 |
| 输出结果 | 选择“质检结论”、合格/不合格/待确认、说明和输出字段 | 逐项结论及单据结论；原始结论保留，不自动审批放行 |
| 结束 | 查看本次输出表格 | 单据汇总、逐项依据和补充实测 |

判定是按每条记录的实际阈值执行，不是给所有产品设置一个统一数值。节点配置可直接查看和修改；数据集内部只负责读取和关联来源记录。字段选择器在按单据汇总后只显示真正保留的分组和汇总字段，避免选择已经不在当前数据中的实测字段。

局域网 HTTPS 使用同样的页面路径，把 `http://192.168.6.16:8011` 换成 `https://192.168.6.16:8443`。客户端仍需信任项目现有局域网证书。

## 已配置的判断口径

### 质检

- 按质检单 `c_qualityInspection` 的 1/2/3 分别进入来料/过程/成品流程。没有混用模板表不同的分类编码。
- 数值明细采用该单保存的运算符与阈值。`lte` 使用上界；源库 `gte` 的阈值实际存于 `c_standardMax`，因此按“大于等于该值”判断，不根据字段名猜方向。
- `between_closed` 两端均包含边界；缺少界限或上下界倒置时进入待确认。
- 对库中准确记录的“夏季≤12.0%，冬季≤14.0%”：不超过 12 时两季都满足；超过 14 时两季都不满足；大于 12 且不超过 14 时等待确认季节。没有自行规定夏冬日期。
- 必检项目按有效模板明细核对。缺少测量、有效项目、模板或必检项目不会被空数据判为合格。
- “结构化项目合格”只代表本次有依据的数值项目和模板完整性检查通过，不等于收货审批或正式放行。
- 原始单据检验结果、是否合格和单据状态保留展示，不用自动复判覆盖。
- 成品发气量、磷化氢、硫化氢的实际值已输出；当前尚无足以直接复判这些单据的完整结构化规则，结果保留待确认。

### 巡检

- 从有效设备/计划关联读取各设备检查项，按“设备 + 计划 + 检查名称 + 检查指标”匹配最新任务明细。同一设备的多个检查项可以同名，不能只按名称匹配。
- 执行主单的计划字段实际保存名称；若该名称对应多个有效计划，标待确认，不任意选择。没有可靠匹配的条目不借用其他设备数据。
- 主变等计划把“正常”“无”“是/否”等写在指标字段；柴油发电机的具体要求写在内容字段，两种存储方式分别处理。
- 明确数字下限如“21V以上”“在10°C以上”采用包含边界的比较。实际值必须来自实际描述字段中单一、带匹配单位的数值，不从“21V以上”标准文本提取 21 当成实测值。
- “实时”“数值”等仅说明采集类型，不是合格阈值；没有上下限时不自动判合格。
- “油位50%以上且无渗漏”等组合条件、油尺格数、分数油位等，缺少可分别核对的测量证据时待确认。“水位距顶部7-8m”原样保留并提示单位需确认，不擅自改成厘米。
- 只有最新任务已完成、记录时间有效、标准一致且原系统明确标正常时，非数值定性项才记为“原系统人工确认正常”；不冒充传感器自动测量。
- 最新任务未完成时逐项待确认，不拿前一条完成记录掩盖本次缺项。
- 周期单独以该计划最后一次已完成巡检时间计算。本次 7 台计划均为 4 小时，画布中的对应关系将代码 2 转换为 4 小时。当前配置覆盖小时、天、周；月/季度/年未按固定天数硬算，出现此类编码时待确认，需补充日历计算配置。
- 回放只按现有副本的时间字段筛选任务，并读取当前标准，不是历史数据库及标准版本还原。历史异常详情仍在原库和既有运行历史；当前逐项结果不是完整的历史异常闭环清单。

### 保养

- 按“设备 + 计划 + 润滑点编号”读取记录；编号为空时按点名关联。计划名称不唯一时待确认。读取数据出现重复结果标识时停止运行，提示核对关联，避免生成重复事项。
- 每个点独立显示润滑周期、油品、用量、方式、换油周期和换油量。本次 25 台设备共有 141 个设备/点关联，不能按全厂统一天数判断。
- 润滑周期字段单位是天；计划周期代码 13/14/15/16/17 分别表示周/月/季/半年/年，没有把代码当成天数。
- 有可靠上次完成时间及有效天数周期时，比较已过天数与周期。
- 不用建档日期、导入日期或空值代替上次完成时间。
- 超过本点周期，或记录油品、方式与本点要求不一致时，走预警分支。未发现这些异常仍不能证明实际执行符合所有要求：复制的油品/用量/方式、加注量与换油执行证据需确认。当前通用节点配置没有自动完成复杂用量范围和单位换算判定，不能将“未超期”输出成“本点全部合格”。
- 库中唯一有效润滑执行明细属于本次 25 台以外的设备，不能拿它作为这些设备的完成基准。因此本次 141 个点均待补执行证据，不宣称全部正常或全部超期。
- 换油周期和量保留展示；缺少独立换油完成日期时不把润滑日期当换油日期。计划总体周/月/年周期保留为上下文；没有可靠总体完成基准时不另行制造总体到期结论。

### 维修

- 未开始/进行中且超过预计完成时间：当前逾期。
- 明确维修失败：异常。
- 已完成但实际完成时间晚于预计：历史超期完成，不计为当前逾期。
- 缺少用于判断的状态或时间：待确认。
- 明确验收不合格或未安装完成时保留警告；验收为空时提示确认是否适用，不自动判为验收通过，也不凭空断言每项维修必须安装。
- 当前 24 条维修记录关联 13 台设备，均已完成，其中 22 条历史超期完成，当前逾期数为 0；24 条验收均未记录，因此保留信息级待确认。

## 仍然依赖业务依据的部分

- 来料让步的扣重阶梯、审批角色及组合规则没有在已核对的结构化配置中得到确认，因此当前不自动让步放行，不采用会议里的举例比例替代正式规则。
- 成品明细的正式判断标准及附件正文尚未确认，当前保留原始值、原始结论和待确认原因。

- 来源是正式环境导入副本，默认参考时间为 `2026-09-02 13:53:59`。这是对静态副本的判定基准，不是生产现场实时状态，也不是任意历史时点的数据库还原。

## 配置备份

- 六个根目录 JSON：公共工作流实际图及节点属性；六个图均不含 SQL、Python 或子流程节点。
- `datasource.json`：业务库和表访问范围，不含账号、密码或私钥。
- `devices.json`：32 台设备、计划、绑定和实际报告索引。
- `device_workflows/`：32 个设备入口的实际工作流定义。
- `device_policies/`：32 个设备策略配置及版本。
- `device_requirements.json`：本次发布时的设备/计划/检查项快照，运行时仍读取源库当前要求。
- [设备要求清单](设备要求清单.md)：32 台设备的入口、各自计划及具体检查项/润滑点要求，便于逐台核对差异。
- `value_datasets/`：十二个读取数据集的实际配置与版本（设备四个、原类别质检四个、按产品模板限定范围的质检四个）；原类别数据集保留供旧流程使用。
- `product_workflows/`：10 套产品检测要求及 2 个未关联单据范围的普通节点图。产品、模板、类别固定在四个读取节点中，开始节点仅接受可选质检单号。
- `../quality_catalog.json`：2026-09-20 按本机 szh_new 核对的目录：16 个产品，7 个产品关联有效模板要求，其中 6 个产品有类别明确的流程入口；12 个流程范围覆盖 3,148 张单据，另 1 个类别缺失模板及其 2 张单据保留为待确认项。目录现有工作区/数据源 ID 保留，未导入或重绑部署工作流。
- `quality_source_snapshot.json`：本机有界只读核对的产品、模板、标准和单据分组证据，含原始报告 SHA-256。运行 `python scripts/rebuild_quality_catalog.py` 从此证据预览目录，`--write` 写入仓库配置；该命令不连接数据库。新的数据变化必须先按数据库边界重新核对，不自动采用旧计数。
- `quality_product_workflows.py`：产品范围配置生成函数；`quality_product_verification.json` 保存全部 3,144 张单据的范围核对及线上运行证据。
- `value_datasets.py`：数据集查询定义，只读关联记录，不作业务合格判定。
- `value_workflows.py`：生成当前可视化图的配置工具，不参与流程执行；所有判断已保存到 JSON 节点属性。
- `quality_value_datasets.py`、`quality_value_workflows.py`：质检读取数据集与可视化图的配置来源；同样不作为代码节点运行。
- `device_assessment.py`、`test_device_assessment.py`：上一版代码节点的历史配置及测试，当前 35 个设备预警工作流均不再执行此代码。
- `verification.json`：当前修订、执行标识、汇总结果和接口验证记录，不包含原始业务数据全集。

这些是当前环境的配置备份，包含环境内资源 ID。迁移到另一套项目时必须重新绑定数据源、设备、策略和工作流入口 ID，不能把原环境 ID 当成新环境已存在的资源。只修改配置生成工具的 Python 文件不会更新已发布流程，必须将生成的节点配置保存到平台并重新发布。
