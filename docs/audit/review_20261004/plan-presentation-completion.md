# 后续实施草案：实际 PPT 页数进入任务验收

2026-10-04，批次十三最终门禁运行期间只读整理。未修改产品或测试，未执行本草案用例。不能计入已修复范围。

## 已读代码与明确边界

- `business_worker/tasks.py`：`requirements` 只保存 type/count；`verify` 按 ready 工件种类计数。
- `business_worker/native_deliveries.py`：原生 present 按真实路径、文件内容指纹登记，文件名后缀决定类型；同路径修改能使旧版本 superseded。
- `modules/artifact/service.py`：标准工件创建统一字体并保存存储指纹，但未记录由文件结构读出的物理页数。
- `modules/presentation/request_constraints.py`：当前助手草稿工具按标题提取明确页数；不识别任意泛指对象，遇歧义不猜测；不是统一任务约束。
- `tests/backend/test_dsh_native_deliveries.py`：有真实一页 PPTX 夹具、真实下载和任务计数，没有用户十五页与物理页数不符的终态断言。
- `tests/backend/test_presentation_request_pages.py`：分批工具路径已覆盖具名文件范围与实际页数；不要删掉这一保护，也不要把这些局部测试误称为顶层验收。

## 先补反例

1. 通过真实 `chat.prepare` 提出“制作一份15页PPT”，原生工作区写入有效一页 PPTX，经 `native_deliveries.present` 保存，`chat.settle(completed)` 不得报告任务全部完成；附件保留可下载，明确差多少页或实际页数不符。原实现预期误报 completed。
2. 同任务改为真实15页文件并重新 present，旧附件 superseded，最终 completed；下载后用 python-pptx 读取15页，不信任文件名、模型文本或输入 metadata。
3. 标准业务渲染路径与原生文件路径遵守相同约束；显式要求是两份不同页数时，各自有来源/目标绑定，不能让一份15页文件同时抵两项。
4. 没有页数要求的合法一页 PPT 不受新增总页数约束影响；询问“如何制作15页PPT”不产生制作义务；文档第15页、PPT第15页修改、正文15页不能混成总页数。
5. 明确范围6–8页允许边界内值；Word页数不能误套PPT；已完成旧任务附件不能跨任务补新要求；修订任务 requires_new_delivery 仍生效。

## 最小实现方向，尚未定稿

- 在服务器保存的业务要求中表示页数约束及其对应对象，保留用户原话证据；单份泛指 PPT 与多个具名 PPT 要分开处理。不要仅凭模型自报 metadata 增加或撤销要求。
- 对存储中的实际 PPTX 读取物理页数。可在标准工件创建时计算并绑定存储 SHA，再由 verify 读取可信证据；历史缺证据工件需要有界检查真实字节，不能猜成通过。
- 若只在 verify 动态检查，仍需限制解压体积、条目数并处理损坏包，避免把模型输出文件当可信 ZIP。字体规范化现有可解析 ZIP 不等于有效演示，更不等于满足用户页数。
- 缺页文件保留，任务为 partial；后续修正后按新物理文件重新判断。不要通过自动重复空白页或复制同页去满足数量。
- 扩展 required_deliveries 时同步审查 schema、队列编辑/恢复、任务历史、前端缺项显示以及显式清单的向后兼容。旧 type/count 请求不应无故报422。

## 本草案不承诺覆盖

页数正确不能证明内容完整、数据准确或每页不同；Word内嵌指定大屏截图/图表需要另建依赖关系及实际关系文件证据，不能以文档里随意一张图片通过。“模型提前结束后自动补齐”另属宿主执行状态机，必须尊重取消、权限变化和结果未知工具的禁止自动重放边界。
