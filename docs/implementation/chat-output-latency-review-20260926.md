## 定位到的功能问题

1. 预警回执包含 46,431 个 Unicode 字符，50 条报告、50 条问题之外，还重复携带长 Markdown 展示正文。原来的头尾截断未提供结构化摘要，每次分页最多 2,000 字符，实际引发 22 次读取。
2. 同一调用在页面上同时显示调用标签与结果折叠行；几十次分页撑满页面。文件既有带内部路径的 Markdown 表格，又有附件卡片。
3. SQL 辅助模型接收整个多文件总任务，当前取数子任务缺乏明确优先级；读取仓库信息时仍执行库存查询。随后 SQL 重定向缓存又允许复用任意前一次同源结果，第三次调用直接返回上一份库存回执。
4. 查询 Excel 固定命名为 `analysis-ID.xlsx`，模型随后把生成工件 ID 传给只识别上传文件 ID 的重命名接口，导致“文件不存在”。
5. 库存结果把空安全库存通过 `CASE ELSE 正常` 显示为正常，缺失阈值不能支持此结论。不同备件的数量相加为 216，也不能作为具有统一计量口径的库存总量。
6. 预警的报告与问题各自分页；50 份报告和 50 条问题不代表工作区全量，也不表示已读完这 50 份报告的所有问题。

## 已实施的修复

- 工具调用、结果和思考内容进入一个默认折叠的处理过程，按工具汇总次数；失败数保留在可见摘要中，展开可查原始回执。真实时间由服务端保存字段提供，刷新后仍可见。
- 仅含已知交付工件的下载表格转换成一组文件卡片，按 ID 去重，保留页数、范围等备注；普通业务表格不受影响。结论与交付文件排在业务明细前面。
- 大 JSON 回执保留完整原始证据，先给结构化概览；支持 JSON Pointer 和选列读取。默认分页 12,000 字符，上限 24,000，读取页本身不再形成第二层截断引用。
- 真实预警回执的离线概览为 3,147 字符。50 条报告按标题、设备、问题数和时间选列后为 5,287 字符，一页可取。完整全文按新默认需要 4 页。上述为同一历史结果的确定性尺寸测量，不能直接换算为新的总耗时。
- `view_device_alerts(..., export_name)` 可将本次已授权结果直接导出为包含报告、问题、来源说明的 Excel，不重复查询、不让模型抄写 50 行。指定问题时可包含其处置日志。
- `export_query_spreadsheet(query_id, name)` 直接确定交付文件名，沿用查询原始数据与来源。
- 缓存只匹配相同子任务，取消 SQL 重定向跨目标复用。SQL 模型明确区分总任务约束与当前取数步骤；元数据召回由子任务主导，同时保留用户明确点名的授权表及连续追问。
- Skills 和 SQL 提示明确空阈值为未知、不同物料/单位不直接相加，并缩短最终回答。此项属于模型指导，尚不是对任意生成 SQL 的语义正确性证明。

## 接口衔接建议

优先建设本项目内部确定性的业务服务：设备预警、库存、物料、仓库名称和计量单位使用明确字段合同；同一份查询回执供 Excel、图表和 PPT 使用。通用语言模型负责理解需求、组织说明与排版，业务数值、分页范围、阈值和单位由接口提供。

本次已打通预警直接导出及查询结果命名导出。库存与仓库字典的专用固定查询、图表/PPT 的数据引用绑定仍需继续建设。目前 PPT 数字主要经模型提交页面规格，不能宣称已经实现全链路确定性数据绑定。外部文档生成接口并不能自行修正内部数据口径，也不能保证降低总耗时。
