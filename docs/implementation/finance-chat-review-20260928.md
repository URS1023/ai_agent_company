# 三段财务会话复核与修复

日期：2026-09-28。

## 真实记录中的差别

用户提供的三个会话分别涉及“财务上个月的营收做成数字大屏”“财务上个月的应收做成数字大屏”，以及“帮我查询财务数据 → 付款 / 应付情况 → 帮我做成数字大屏”。

本次从本机 `storage/dsh-host/sessions` 的原生持久化日志读取真实用户消息、工具调用与回执，未重新运行这些业务查询。裁剪重复流式片段后的证据保存在 `.implementation/chat-finance-review-20260928/`。

| 请求 | 日志中的执行情况 | 原有耗时 |
| --- | --- | --- |
| 上个月营收大屏 | 主要查询销售订单，按 2026 年 8 月过滤，无对应订单记录；没有创建大屏 | 110.389 秒 |
| 上个月应收大屏 | 主要查询销售合同，按 2026 年 8 月签约日期过滤，返回空结果；没有建立应收余额口径，没有创建大屏 | 122.139 秒 |
| 三句话逐步处理 | 付款审批台账，未限定月份；最终生成付款与应付大屏 | 三轮分别 19.743、61.660、46.387 秒 |

三句成功的查询与另外两句的业务方向和时间条件不同，不能据此认为“同一个应收任务拆句后就查到了”。同样，销售订单或合同的某月查询为空，不能证明该月没有营收或应收。

## 已由记录确认的问题

1. **诊断查询被改回业务查询。** 营收日志 seq90、应收日志 seq71 请求核对全部月份的覆盖范围，实际回执标记 `requested_mode=sql / executed_mode=natural_language`，最终 SQL 又带上 8 月筛选。营收最终回答却仍把结果称为“全表按月汇总为 0 行”。
2. **候选检索被夸大为全库不存在。** schema 仅返回 12 张相关表，模型最终声称“全库没有应收／回款表”。源发现的目录信息明确显示完整业务表数量远大于 12，现有证据不足以作出不存在的结论。
3. **关系元数据错误。** 应收第一条 SQL 将销售合同客户标识连接到客户名称。保存的旧低代码 reference 关系也采用了该显示字段；另有合同编号与合同标识混淆。左连接不是该次空结果的直接原因，但有数据时会造成客户名称或分组错误。
4. **表结构读取重复。** 营收共 11 次 `read_tool_result`，其中 9 次围绕同一字段投影；45,091 字符的原文累计向模型返回 79,091 字符。从首次 schema 到首次实际取数耗时 52.217 秒。
5. **字段投影改变后页码失效。** 应收先读取完整 columns，再切换为只有表名和注释，却继续使用旧 offset；新投影只有 717 字符，导致两次分页越界失败。
6. **交互和表述问题。** 应收最终的同一个正文块包含大段英文自我推演；三句会话在用户只要求查看时生成了四份 Excel，并重复询问已选数据源。上述现象不能靠折叠前端 reasoning 区域解决。

## 修复内容

- `read_tool_result` 概览先保留候选表名、字段数量和单表 JSON Pointer，避免宽表使所有表名都被摘要丢弃。候选索引完整不等于全库目录完整。
- 续页增加绑定引用、JSON Pointer 和字段选择的游标及 `next_read` 参数；字段选择改变时旧游标无效。旧 offset 越界错误会给出有效长度和从 0 重读的明确参数，不再只报笼统错误。
- 增加独立的单表日期覆盖诊断模式，查询记录数、空日期数和日期起止。诊断明确不代表业务金额，也不替换正式查询的月份、部门等条件；同轮相同诊断复用成功结果。
- 旧低代码关系只根据明确且唯一的业务主键证据修正标识端，并保留原始声明和修复依据；不能确认时不提供猜测的 JOIN 键。真实数据库外键继续以其完整字段组为依据。
- 元数据检索与提示压缩纳入宽表后部的命中字段，返回检索覆盖信息；复合主题保持有限候选预算并分别保留直接命中表。
- 提示及业务技能明确区分营收、应收、回款、应付、付款台账和合同金额；按实际执行的 SQL 解释结果。中文正文不输出自我推演；只查询时不主动制作文件，已选单一数据源不再要求重新选择。

## 历史读取异常与验证边界

本次初始读取本机 `company_agent` 的三段历史时，带大段消息正文／JSON 的排序查询返回 MySQL **1038：排序内存不足**。当时已核对本机 MySQL80 服务归属，随后立即结束连接并停止真实数据库测试；单次残留查询检查确认已无该查询运行。未扩大超时、修改数据库参数或重试原 SQL。

生产历史接口存在同类整行排序路径，已改为先排序轻量主键，再分批无排序读取正文与 JSON，最后恢复原顺序。此改动覆盖消息、运行和事件历史，以及继续任务和恢复队列的相邻读取。

1038 后先完成隔离 SQLite、纯函数和本机模型桩验证，再向用户说明异常和具体复验范围。用户本轮明确回复“允许本机小范围复验并更新服务”后，才恢复以下一次性本机检查。
