4. 工作流前端 `BlockEnum` 共 **32 个类型标识**，其中包含占位、迭代/循环内部节点和兼容别名；不能宣传为“32 个独立可添加节点”。完整标识见下表。

6. 本轮零数据库连接、零服务启动、零模型请求、零业务代码改动。功能可用性依据页面、组件、控制器及服务实现的静态对照，尚未逐操作动态验收。

## 部署与完整复用方案

本地前端 `web/package.json:3` 标记版本 `1.17.1`。建议先固定当前源码基线及依赖锁，再做 fork；版本号本身不能证明这是完整、干净的官方发布版本。

`docker/docker-compose.yaml` 已核对到 api（227）、api_websocket（277）、worker（309）、worker_beat（356）、web（390）、db_postgres（428）、redis（495）、sandbox（513）、plugin_daemon（577）、agent_backend（664）、agent_ssrf_proxy（703）、ssrf_proxy（731）、nginx（776）服务定义。向量存储等可选服务还需按部署配置选择。本轮仅读取文件，不读取真实密钥，不启动任何服务。

建议的具体做法：

1. 保留 Dify 的 React/前端、Python API、任务队列、插件服务、Agent 后端及 Agent Runtime，先确保原生功能基线可在获准的本地环境验收。
2. 新平台外壳按 qKnow 视觉与业务分类提供“AI 对话、应用/Agent、工作流、知识、设备/产品、数据/报表”等入口；Dify 模块先作为独立子系统通过同域路径/导航接入，再逐步统一设计 token 和业务上下文。iframe 可用于短期验证，正式架构须验证登录、路由、文件和 WebSocket/SSE，不预设 iframe 就能全部解决。
3. Open WebUI 负责用户对话入口与其 Agent/工具执行方式；Dify 负责自己的 Agent 构建/运行与固定流程。两套 Agent 按业务场景并存，通过工具或明确 API 适配调用，不互相替代、不复制一套简化内核。适配层传递身份、授权对象、会话/任务关联、输入文件与结果资源引用。
4. 统一目录登记“来源系统、资源 ID、版本、访问范围、调用协议”，底层各系统保留自己的真实存储与资源模型。知识库建议以 Dify 为主要知识构建与检索入口，Open WebUI 经适配访问；原 Open WebUI 原生知识能力仍保留，通过入口与资源来源标识避免同名数据混淆。
5. 设备质检、产品质检和数据处理通过 Dify HTTP/Tool/MCP 节点调用领域服务，领域服务返回结构化检查结果、证据、标准版本和业务记录 ID。业务页面、报表和聊天引用同一业务记录；不能用自然语言回答替代业务落库与失败状态。
6. 先验证跨系统链路：Open WebUI 发起任务 → Dify 已发布流程/Agent → 领域工具 → 结果保存 → 结构化成果回到聊天及业务详情。另验证“无聊天也能执行”的定时触发与人工复核。
