# 企业AI数字化｜制造业（食品 / 化工 / 纺织）整体方案
> 核心逻辑：**先夯实数据底座（IoT+MES/ERP），再落地小场景AI，逐步用行业大模型+数字孪生做全链路决策**；三个行业共性是降本、提质、安全，差异在合规、风险、质检侧重点。

## 一、行业AI数字化落地场景
### ✅ 食品制造业（强安全、强追溯、供应链长）
1. **AI视觉质检**：异物检测、包装缺陷、外观霉变、标签错漏；高速产线实时识别，替代人工灯检。
2. **工艺智能优化**：烘烤/杀菌/发酵参数AI寻优，稳定风味、降低能耗，减少批次波动；AI辅助配方研发、风味预测、营养配方生成。
3. **安全生产+合规监控**：多模态AI摄像头识别违规操作（未穿戴工服、区域闯入）；温湿度、洁净区环境异常预警。
4. **全链路溯源**：IoT采集原料、加工、仓储、冷链数据，AI做供应链风险预测；产品问题一键溯源到批次、原料来源。
5. **仓储与排产**：AI-APS智能排产，应对多SKU柔性生产；WMS+AI预测原料损耗、库存周转、保质期预警。

> 行业痛点：原料波动大、食品安全法规严苛、批次召回风险高；中小企业设备老旧，数据采集难度大。

### ✅ 化工制造业（高危、连续流程、设备为重）
1. **工艺自适应优化**：采集温度、压力、流量、pH等传感器数据，机器学习/强化学习动态调参，提升收率、降低副产物与能耗；产品质量预测。
2. **设备预测性维护PdM**：振动、声学、红外+AI模型，提前预警泵、反应器、管道腐蚀、结垢，减少非计划停机。
3. **安全风险AI预警（重中之重）**：知识图谱+数字孪生，泄漏、有毒气体、火焰、人员越界实时识别；模拟爆炸/泄漏扩散，自动生成应急处置方案；危化品仓储风险评估。
4. **新材料研发AI**：AI分子模拟，筛选配方、预测材料性能，大幅缩短实验试错周期，降低研发成本。
5. **能耗与碳管理**：AI能耗建模，动态优化蒸汽、电力消耗，辅助碳盘查、绿色低碳管控。

> 行业痛点：安全红线不可触碰；机理复杂、数据多但标准化差；老设备改造难度高，数据孤岛严重。

### ✅ 纺织制造业（劳动密集、视觉质检为主、能耗高）
1. **AI视觉验布**：坯布疵点（破洞、跳纱、污渍）自动检测与分类，替代人工验布；染布色差AI识别、AI测配色，减少打样次数。
2. **生产与工艺优化**：AI优化定型、染色工艺参数，降低水、蒸汽、电消耗；数字孪生模拟织造流程；订单智能排产，柔性小单快反。
3. **设备预测维护**：织机、纺纱设备振动/电流AI分析，预警断纱、机件磨损，减少停机。
4. **供应链与研发**：AI辅助花型设计；消费数据反向驱动款式预测；库存与面料损耗预测。
> 标杆案例：织慧云台，AI优化定型机，单位产值碳排放下降22.7%，不良品率降低15.25%
> 行业痛点：多品种小批量、人工质检成本高；印染环节环保压力大。

## 二、共性落地架构（通用四层）
1. **感知层（底座先行）**
传感器、工业相机、5G工业网关，采集设备、环境、质量、能耗数据；老旧产线优先做低成本数据采集，不要一步到位全换新设备。
2. **平台层**
工业互联网平台，打通ERP/MES/WMS/LIMS，消除数据孤岛；建立时序数据库、图像库，做数据清洗标注。
3. **AI应用层（大小模型协同）**
- 小模型：机器视觉、时序预测、故障预警（优先落地，见效快）
- 行业大模型：工艺知识库、安全问答、生产文档检索、异常根因分析、智能数字员工
4. **决策与执行层**
数字孪生大屏、自动下发工艺参数、预警推送、工单自动生成，形成**感知→AI预测→决策→执行→数据反馈**闭环。

## 三、落地实施路线（建议分三阶段，降低风险）
> 不建议直接上大模型，**小场景先行，价值验证后再扩面**
1. **阶段1：数字化筑基（3–6个月）**
盘点产线，打通核心系统，采集关键数据；优先选单一高痛点场景试点（食品异物检测、化工设备预警、纺织验布），做最小可行性项目MVP，测算ROI。
2. **阶段2：规模化AI复制（6–18个月）**
把验证成功的AI场景复制到多条产线；搭建企业知识库，接入行业大模型做文档、工艺、安全的问答分析；建立数据治理规范。
3. **阶段3：全链路智能决策（18–36个月）**
数字孪生工厂，全局智能排产、供应链协同、全局能耗/安全优化；企业智能体自动跨系统调度。

## 五、常见踩坑提醒
1. 跳过数字化直接上AI大模型：MES/数据采集不完善，模型无高质量数据，项目极易失败；
2. 一次性全工厂改造：投入巨大，ROI不可控；**单点MVP验证是制造业AI数字化最稳妥路径**；
3. 忽视行业机理：纯通用大模型不懂工艺，必须**机理模型+数据驱动混合建模**，尤其化工、发酵类流程；
4. 缺少运维与标注团队：工业AI需要持续标注、模型迭代，不是上线就一劳永逸。

# 前提：已有数字化基础（ERP/MES/SCADA/WMS/LIMS、数据已经采集入库）
核心结论：**数字化解决“看得见、存得住”；AI化解决“会预测、会寻优、自动决策”**。
不用推倒现有系统，AI不是替换MES，而是**在现有数字化底座之上叠加AI能力层**。
整体思路：**现状盘点 → 痛点分级 + 数据资产评估 → 优先落地高ROI的小模型场景 → 沉淀行业知识库 → 引入工业大模型做根因/文档/知识推理 → 构建闭环自优化体系**

## 一、第一步：盘点现有数字化资产（1~2周完成，决定AI能不能跑）
你已经有数字化，第一件事不是买大模型，而是评估数据质量。
### 1）系统与数据流盘点
- 已有的系统：MES、SCADA、ERP、WMS、LIMS、QMS、设备管理系统
- 数据链路：能不能自动拉取，还是需要人工导出Excel？数据是否实时？
- 数据类型分类
  - 时序数据（化工温度压力、设备振动、能耗、食品发酵曲线）：最适合时序AI、预测性维护、工艺优化
  - 图像视频数据（质检摄像头、现场安防摄像头）：机器视觉
  - 业务结构化数据（工单、批次、质量记录、库存、订单）：预测、排产、异常统计
  - 非结构化文档（SOP、工艺卡、应急预案、设备手册、历史事故报告）：大模型知识底座

### 2）数据质量打分（关键）
重点看这4个指标：
1. 完整性：关键变量有没有大量缺失？（比如工艺参数经常断采）
2. 标签：有没有历史事件标注？例如：哪些批次是不良品、哪次停机是轴承损坏、哪组参数导致发酵失败
3. 一致性：MES和SCADA时间戳是否对齐，单位是否统一（很多工厂数字化做完，但时间不同步，AI直接失效）
4. 相关性：有没有记录**根因**，不只是结果。只记录“良品率低”，但没有同步当时温度/压力/原料批次，AI很难找到规律

> 结论：数据质量好 → 直接上预测、优化模型；数据采集齐全但标签不足 → 优先做**弱标注、半监督模型**，或者先做知识类大模型应用（不需要大量标注）

### 3）业务痛点打分，做优先级排序（按ROI、实施难度）
打分维度：**损失大小、数据可用度、改造工作量、合规风险**
> 高优（快见效，优先MVP）：
> 设备预测性维护、AI质检、能耗异常预警、质量异常根因检索
> 中优：APS智能排产、工艺参数寻优、原料品质预测
> 慢重（后面做）：数字孪生全局优化、全流程自主闭环控制

## 二、第二步：AI分层落地策略（已有数字化底座，分3层推进）
### 第一层：感知型AI（轻量，最快落地，1~3个月MVP，工业小模型）
**目标：从“事后记录”变成“实时告警、识别异常”，不需要改动核心控制系统**
复用你现有数据/摄像头，对接MES/SCADA接口。
适用三个行业：
1. 机器视觉：质检、现场合规（未穿戴防护、区域闯入）
2. 时序异常检测：实时识别工艺偏离、设备异常振动、能耗突变
> 输出：预警消息推送到MES工单、移动端；只告警，**不直接干预生产**（安全风险低，工厂最容易接受）

✅ 特点：数据来自现有数字化平台；模型是专用小模型；可独立试点，见效看得见。

### 第二层：预测&优化AI（中等复杂度，3–9个月，数据驱动+机理结合）
**目标：从“发现异常”升级为“预测未来、推荐最优参数”**
利用历史批次、传感器时序数据训练模型。
- 化工：预测产品纯度、收率；预测设备剩余寿命RUL；给操作工推荐最优温度/压力区间
- 食品：预测批次风味、保质期、不良概率；发酵工艺参数寻优
- 纺织：预测次品率；染色配方参数推荐、能耗预测

> 重点区分两种模式
1. **推荐模式（推荐参数给操作工人工确认）**：风险低，首选；AI给出建议，人审核后下发MES
2. **闭环自动调参**：AI自动下发参数到SCADA，**高危行业（化工）谨慎上，需要安全联锁保护，分阶段放开权限**

### 第三层：工业大模型（知识推理层，6~18个月，和上面两层并行建设，不要单独先上）
大模型**不做实时控制**，核心用来处理工厂非结构化知识，和小模型互补。
能力：
1. 工艺知识库问答：SOP、操作规程、设备手册、历史事故、批次异常报告检索；操作工/工程师自然语言提问
2. 异常根因分析：MES+SCADA异常数据丢给大模型，自动检索历史相似案例，给出可能根因和排查步骤
3. 智能数字员工：自动读取MES日报，生成生产报表、质量分析报告、设备周报；自动汇总工单
4. 文档处理：解析PDF工艺变更、安全文件，提取参数，入库到数据平台

> 重要提醒：**不要拿通用大模型直接接入生产，必须做私有化部署、行业知识库微调、提示词管控、结果校验，避免幻觉**。

## 三、技术架构（在你现有数字化平台上叠加，不用替换MES）
```
现有层：ERP / MES / SCADA / WMS / QMS / 时序库、图像库
        ↓ 标准API接口、数据订阅（ODBC/MQTT/Kafka）
【AI中台层（新增）】
    1. 数据服务模块：数据对齐、特征工程、特征库（复用已有数据治理成果）
    2. 模型管理MLOps：模型训练、版本管理、A/B测试、监控（模型漂移监控，工业AI重中之重）
    3. 模型仓库：小模型（CV、时序预测、RUL） + 私有化行业大模型
        ↓
【AI应用服务】
    质检服务、设备预警、工艺推荐、根因分析、智能报表、知识问答
        ↓
推送回原有系统：MES工单、大屏、移动端告警
```
> 关键点：MLOps必须配套。工业数据随原料、季节、设备老化持续变化，模型会**漂移失效**，数字化时代很少考虑这件事，但AI化必须持续监控模型精度。

## 四、落地实施路径（已经数字化，路线缩短，跳过基础采集阶段）
### 阶段1：AI试点MVP（1–3个月）
1. 选定**单一产线、单一痛点场景**（不要全工厂铺开）
    举例：化工选泵预测性维护；食品选包装视觉质检；纺织选AI验布
2. 接口打通：从MES/SCADA拉历史数据，做特征工程，训练模型
3. 试运行：AI输出结果并行对照人工，不接管生产，验证指标（漏检率、预测准确率）
4. 评估ROI，形成可复制模板

> 目标：拿到可量化指标，说服管理层，沉淀一套工厂AI数据接入规范

### 阶段2：规模化复制 + 搭建企业知识底座（3–12个月）
1. 将验证成功的AI模型批量部署到其他产线
2. 把工厂SOP、历史故障、批次报告全部入库，搭建私有知识库，上线工业大模型应用（报表、根因检索）
3. 建立MLOps运维流程，固定模型迭代、漂移监控机制
4. 逐步把AI推荐结果集成进MES界面，操作工在原有系统直接看到AI建议，不用换系统

### 阶段3：局部闭环自主优化（12–24个月）
在安全可控前提下，**局部场景**实现AI推荐参数自动下发（化工要做硬安全联锁），跨工序协同优化；可接入数字孪生做仿真推演。

- 约束：多SKU，原料批次波动大，模型要支持快速适配新面料

## 六、高频踩坑（已经数字化的企业最容易踩）
1. **数据打通了，但时间戳不同步、单位混乱**：MES时间和SCADA差几十秒，时序AI直接失效；数字化不等于数据可用于AI
2. **直接采购通用大模型，期望解决工艺优化**：大模型擅长文字推理，**不擅长高精度实时工艺预测**；工艺优化必须时序小模型+机理方程结合
3. **只上线模型，不做MLOps和模型漂移监控**：设备老化、原料变化，半年后模型精度大幅下滑，没人维护，项目停滞
4. **忽略人的流程**：AI算出推荐参数，但操作工不习惯在MES看AI结果，不采纳；需要改造原有操作界面、建立考核机制
5. 想一步到位全链路优化：**单点验证成功再复制**，哪怕数字化基础很好，AI也不能一次性全厂上线

# 工业AI通用平台（面向食品/化工/纺织制造业，已有数字化底座，可按需适配不同企业、后续调优）
定位：**不是成品AI应用，是一套可插拔的工业AI能力底座**。
目标：客户企业只需要接入自身MES/SCADA/相机，在平台上配置、选择模型、编排流程，就能快速搭建各自AI场景；支持食品、化工、纺织不同行业按需二次调整，**平台内核通用，业务层插件化**。
> 一句话区分：数字化平台负责业务记录；这个**工业AI通用平台负责模型管理、特征管线、推理服务、告警编排、知识服务**。

## 二、平台必备模块清单（必须内置，保证通用性）
### 1. 多源数据接入&适配模块（重中之重，做通用平台第一块）
目的：对接不同企业五花八门的现有数字化系统（每家MES厂商不一样，SCADA协议不一样）
- 协议网关：OPC UA、MQTT、Kafka、Modbus、HTTP Rest、JDBC/ODBC
- 流/批双模式：实时传感器流 + 离线历史批次数据导入
- 时间对齐组件：自动对齐多系统时间戳、统一时间粒度（1s/1min/5min），自动处理时间偏移（制造业高频坑）
- 数据映射器：可视化配置，把客户字段映射到平台标准字段，**不用改平台代码**，客户在页面配置即可
- 数据质量规则引擎：可配置校验规则，缺失、跳点、超范围自动标记，输出数据质量报告

### 2. 可视化特征工程平台（通用平台核心）
不同行业AI，本质差异就是特征。平台提供通用特征算子，客户/实施人员拖拽配置，不用写大量Python代码：
- 时序算子：滑动平均、差分、导数、统计聚合、频谱提取（振动信号）
- 预处理算子：归一化、缺失填充、异常过滤
- 特征版本保存：一套产线的特征方案保存为模板，同类产线直接复用
> 价值：接入新企业，只需要配置特征，不用重构平台。

### 3. MLOps全链路模块（平台核心，支撑所有AI模型）
**一套统一的模型生命周期管理，同时支持CV、时序预测、工业大模型**
1. 数据集管理：按租户隔离，支持时序数据集、图像数据集、文档知识库
2. 训练工作台：
    - 内置通用算法模板（无需从零开发）：IsolationForest、LSTM/TCN、XGBoost、Transformer时序、YOLO系列CV
    - 支持自定义代码脚本（专家模式，满足化工机理混合建模等高级场景）
3. 模型版本管理、模型打包、一键发布推理服务
4. **模型监控模块（工业场景必选）**
    - 数据漂移、概念漂移监控，自动报警
    - 推理结果指标监控（准确率、召回率）
    - 推理日志全留存，审计溯源（食品/化工合规审计）
5. 批量推理 + 实时推理双引擎
    - 实时：视频质检、实时传感器异常告警（毫秒级）
    - 批量：每日批次质量预测、寿命预测

### 4. 插件化模型市场（业务层，实现“通用底座+按需行业能力”）
平台内核不动，业务能力做成独立插件，**新行业只开发插件，不改动底层**
- CV插件框架：图像采集、预处理、推理、结果分类。不同质检模型（异物/疵点）作为插件导入
- 时序预测插件框架：RUL、质量预测、能耗预测模板
- 工业知识大模型插件（独立模块）
    - 私有知识库引擎：文档解析（PDF、Word、图片OCR）、向量库
    - 检索增强RAG引擎，提示词模板管理
    - 知识问答、根因分析、文档摘要、自动报表Agent
    - 安全管控：幻觉校验、结果引用原文、可审计，适合化工安全、食品SOP查询

> 关键设计原则：**大模型只是平台其中一个插件，不是平台主体。平台同时支持传统机器学习、CV、RAG大模型**

### 5. 低代码业务编排引擎（非常关键，用来适配不同企业业务规则）
客户业务逻辑千差万别：同样是设备告警，A企业推MES工单，B企业发短信+大屏。
- 可视化拖拽编排：AI推理输出 → 条件判断 → 动作（告警、回写MES、生成报告、推送钉钉/企业微信）
- 可配置业务规则：阈值、分级告警、工单路由规则
- 开放Webhook/API，和客户原有系统双向打通
> 好处：对接新企业，业务流程靠配置，不需要大量定制开发

### 6. 应用门户层（通用）
- 统一工作台、自定义可视化大屏（拖拽图表）
- 告警中心、消息中心、报表模板引擎
- 细粒度权限：租户、项目、角色、数据行级权限
- 审计日志：所有数据访问、模型推理、操作记录留痕（食品/化工合规硬性要求）

### 7. 底层运维&安全模块（平台底座）
- 容器化编排（K8s）：模型服务弹性扩缩容，不同模型独立容器，互不影响
- 资源调度：GPU/CPU算力分配，CV推理、大模型推理算力隔离
- 安全：传输加密、存储加密、租户数据隔离、API鉴权
- 部署模式支持：私有化部署（制造业主流）、本地边缘部署（产线侧低延迟场景）、云端SaaS可选

2. CV视觉模板

    - 现场合规行为识别（安全帽、工服、区域闯入）模板

## 四、平台设计核心原则（做通用平台最容易踩坑的地方）
1. **内核稳定，业务插件化**
    底层数据、MLOps、推理引擎尽量少改；行业业务逻辑全部封装为插件/配置。新增行业只新增插件，不修改平台底层代码。
2. **配置优先，代码为辅**
    80%客户场景通过页面配置完成；20%高级场景（化工机理模型）开放自定义脚本入口，**不能所有场景都写定制代码，否则就变成项目制，不是平台**。
3. **解耦：平台不绑定任何特定MES/SCADA**
    只做标准适配器。每家客户MES不同，通过配置映射表对接，平台不内置某家MES硬编码。
4. **区分「平台内核」和「项目实施包」**
    - 平台内核：一套，统一迭代升级
    - 实施包：每个企业独立，包含：客户数据映射、特征配置、模型版本、业务编排规则、看板配置。实施包可导出导入，快速复制到同行业其他客户。
5. **模型和业务解耦**
    模型输出结构化结果（比如：缺陷类型、故障概率、预测良品率），**业务决策逻辑交给编排引擎配置**，模型只管推理，不写业务规则。

WorkBuddy核心是**MCP Skill + Agent沙箱任务执行器**，能自主调用工具、读写业务数据、拆解多步骤任务，交付文件/报表/分析结论；
你的组合：

## 一、各组件职责划分（避免重复造轮子，明确边界）
### qKnow【知识中枢，你的核心壁垒】
- 承载：工厂SOP、工艺手册、设备图纸、事故报告、历史批次异常案例、安全预案
- 能力：向量检索 + **知识图谱（实体：设备、工序、原料、故障；关系：故障-根因、参数-质量）**，这是纯Dify做RAG很难做好的工业可解释推理
- 对外输出API：知识检索、实体推理、溯源查询；**Dify调用qKnow作为一个工具**
> 优势：化工/食品异常根因分析、设备故障排查、合规文档审查，天然适配你的制造客户

### Dify【Agent编排内核，对标WorkBuddy Harness】
**作为整个平台的业务逻辑调度中心**
1. Workflow可视化编排：任务拆解、多步骤串行并行（比如：拉MES批次数据 → qKnow检索相似历史案例 → 调用自研报表引擎生成质量分析报告 → 推告警工单）
2. 工具注册中心：注册三类工具
   - 工具1：qKnow知识检索API
   - 工具2：自研NoSQL报表引擎（查询MES/SCADA数据，生成图表、报表）
   - 工具3：外部连接器（OPC UA/MQTT/MES/ERP Webhook）
3. Agent运行时：规划、反思、工具调用循环、上下文管理、提示词管理、应用模板管理（食品/化工/纺织预制Agent模板）
4. 审计日志、追踪Trace（每一步调用记录，满足食安、化工安全审计，制造业硬性要求）

> 注意：Dify负责**任务规划与工具调度**，不要让Dify再重复做知识库，知识库全部下沉给qKnow。

### Open WebUI【前端对话工作台 + 模型网关层】
- 统一模型接入层：集中托管所有模型（本地私有化大模型、云端API、多模型切换），Dify和OpenWebUI共用一套模型池，避免重复部署推理服务
- 面向终端用户对话界面：操作工/工艺工程师直接聊天、上传附件、模型参数调整
- 内置Function Calling，可直接调用Dify的Agent应用
- 角色隔离：管理员、工艺员、设备员、访客不同对话空间

> 边界：**OpenWebUI是聊天入口，不做复杂业务编排；复杂任务交给Dify Agent**

### 自研NoSQL报表生成模块【制造结构化数据引擎，你的工业特色模块】
> 为什么要自研：通用BI（Metabase、Superset）无法和Agent深度联动，无法自然语言直接查询MES/SCADA时序+业务数据，并且很难私有化、审计留痕。
- 底层：NoSQL（MongoDB/InfluxDB时序）存储工厂业务/时序数据（对接MES、SCADA、WMS）
- 能力：自然语言转查询（NL2Query），读取生产批次、能耗、设备、质量数据
- 输出：自动生成生产日报、批次分析、质量异常报表，导出Word/Excel/图片图表
- 对外暴露API，作为Dify的一个工具：`get_factory_report(指标,时间范围,产线)`
- 必须自带：数据行级权限控制（A客户只能看自己工厂数据，同工厂操作工只能看本产线）

## 二、整体数据流（完整Agent闭环，对标WorkBuddy任务执行链路）
```
用户（操作工/工艺主管）→ OpenWebUI对话界面
    ↓
Dify Agent接收自然语言请求，做意图拆解
    ↓ 自动选择工具
    ├─【工具A】调用qKnow：检索工艺文档、故障案例、知识图谱推理根因
    ├─【工具B】调用自研NoSQL报表引擎：拉MES/SCADA时序、批次业务数据，生成图表
    └─【工具C】外部连接器：回写工单、推送告警到MES
    ↓
Dify汇总所有工具返回结果，交由大模型综合整理
    ↓
输出：分析结论 + 报表附件 + 根因建议，返回OpenWebUI给用户
    ↓
全链路日志存入审计库（谁、什么时间、调用了哪些数据、模型返回内容，满足食品化工合规审计）
```

## 三、对标WorkBuddy，你现在方案缺的4个关键模块（必须自研补齐）
WorkBuddy核心不是聊天和知识库，是**安全可控的任务执行沙箱 + 权限上下文继承 + Skill/连接器管理 + 任务托管**，这是开源三件套天然缺失的地方。

### 1. 安全执行沙箱（最高优先级）
WorkBuddy有独立隔离沙箱，限制Agent执行能力，防止AI随意调用危险接口、篡改业务系统。
你需要自研：
- 工具调用权限矩阵：**同一个Agent，A角色可以查询MES，不能写MES；管理员才允许回写工单**
- 动作黑白名单：禁止高危操作（化工场景：禁止AI直接下发工艺参数，只能生成推荐，人工确认）
- 超时、资源限额、任务中断/回滚机制，防止Agent死循环调用接口
> 制造业红线：**Agent不能无权限随意写生产系统**

### 2. 统一身份&数据权限上下文
WorkBuddy最大企业级特性：**对话继承登录人的权限**，AI只能访问当前用户有权限看到的数据。
- SSO单点登录：Keycloak/自研账号系统，统一Dify、OpenWebUI、qKnow、报表引擎
- 行级数据权限：租户隔离（多客户SaaS），工厂、产线、数据权限跟着用户session传递
> 坑：Dify、qKnow、OpenWebUI各自独立权限系统，默认不会打通；如果不做统一权限，多客户部署会出现数据泄露风险。

### 3. 标准化Skill/连接器框架（对标WorkBuddy MCP）
WorkBuddy用MCP协议统一管理外部工具（文档、数据库、业务系统）。
你不需要完全上MCP，但要定义**统一工具协议**：
- 标准化工具描述、入参、出参、权限声明
- 可视化注册新连接器（OPC UA、MES、WMS），后续接入新工厂只配置，不修改Dify底层
- 预制行业Skill包：食品批次分析、化工设备根因、纺织疵点分析（就是你之前的行业插件）

### 4. 任务托管与长任务调度（Managed Agent）
WorkBuddy支持后台托管Agent，定时执行、长任务后台跑，比如每日凌晨自动拉取MES数据生成生产月报。
Dify工作流可以做，但原生缺少：
- 任务进度持久化、暂停/恢复
- 定时触发器、周期性任务调度
- 任务失败重试、告警通知

# 核心思路修正 & 边界定义
> 一句话：**主数据从客户已就绪数据库（MES/SCADA/WMS/业务库）读取；缺失、非结构化、无法直接查询的信息，交给 qKnow+Dify+OpenWebUI 做知识补齐与推理补全。**
这个模式非常适合制造业POC，也刚好匹配你对标WorkBuddy的定位：**结构化事实以数据库为准（可信源），AI只负责“补背景、补解释、补SOP、补推理、补报告文字”，不篡改原始业务数据。**

> 关键原则：**数据库 = 唯一可信事实源；AI组件只做补充，不能覆盖/改写库内真实数据。**
> 客户问：3号产线本周良品率多少 → 优先查数据库；
> 客户接着问：良品率下跌一般是什么原因、该怎么排查 → 这部分缺失的工艺知识、历史案例，由 qKnow 补齐，Dify编排推理。

## 一、数据流分层：区分【可信数据】和【AI补齐数据】
```
用户在OpenWebUI提问
        ↓
Dify Agent做意图拆解，判断信息类型
├─【事实类量化指标】→ 调用自研NoSQL报表引擎 → 查询客户就绪数据库（时序/业务库）
│    返回：批次、产量、良品率、能耗、设备运行时长（**不可AI编造**）
└─【知识/推理/解释类（数据库没有）】→ 调用qKnow（RAG+知识图谱）补齐
     返回：SOP、故障根因、工艺原理、历史同类事故、处置步骤、合规条款
        ↓

        ↓

        ↓
```

### 信息划分清单（直接用于提示词和工具路由规则）
✅ **必须从数据库读取（禁止AI编造）**
- 生产时序：温度、压力、振动、能耗、启停时间
- 业务结构化：工单、批次号、产量、不良数量、库存、设备维修记录
- 报表原始数值、时间范围统计、图表数据

✅ **数据库不存在，交给AI栈补齐**
1. 静态工艺知识：SOP、操作规程、设备手册、图纸说明、安全预案
2. 历史案例：过去同类异常的根因分析、处理方案（文档形式，不在业务库）
3. 推理解释：为什么指标异常、排查步骤、风险评估、工艺理论解释
4. 文本生成：报告分析段落、建议、总结、邮件、工单备注
5. 术语释义：工艺名词、设备部件、法规条文

> 重要规则写进Dify Agent系统提示词：
> > “所有数值、产量、批次、传感器指标，优先调用数据查询工具从业务数据库获取，**严禁直接编造数字**。数据库查询返回空/无结果时，明确告知用户【数据库无该记录】，再使用知识库补充参考信息，并标注【参考知识，非实时业务数据】。”

## 二、组件职责重新对齐（适配“数据库优先，AI补齐”模式）
1. **自研NoSQL报表引擎**
    唯一对接客户业务数据库，做NL2查询、指标统计、图表生成；
    只输出客观数据，**不做主观推理**；查询失败/数据缺失返回明确标记 `data_missing: true`，这个标记作为Dify的判断条件。

2. **Dify（Agent编排核心）**
    - 先调用报表引擎拿量化数据；
    - 如果返回 `data_missing`，或者用户问题需要工艺/故障背景，自动调用qKnow；
    - 合并结果，强制**来源标注**：【业务数据库】【工艺知识库参考】；
    - 控制分支逻辑：区分“数据查询分支”和“知识补齐分支”；
    - 保存Trace，记录：哪部分来自数据库，哪部分来自知识库。

3. **qKnow（知识补齐专用）**
    只承载**数据库之外的文档、图谱**；不存储业务生产时序/批次数据。
    当数据库缺少背景、原理、案例时，qKnow输出参考材料，作为补充论据。

4. **Open WebUI**
    对话交互层：展示数据库图表 + AI补充的知识文本；
    支持用户上传新文档，存入qKnow，用来**扩充后续补齐素材**；
    模型网关，负责模型调度，不做业务数据查询。

## 三、两种典型业务场景演示
### 场景1：工艺工程师提问：“上周2号反应釜纯度下降，请分析原因”
1. Dify：意图识别 → 先调用报表引擎，查询数据库：上周2号釜温度曲线、进料流量、纯度检测值；
2. 拿到真实数据，发现周三温度超上限；
3. Dify自动调用qKnow：检索【反应釜温度超标对应的故障案例、SOP处置流程】；
4. Dify合并：数据库数据（纯度、温度曲线图表）+ qKnow检索到的历史案例和排查步骤；
5. 输出到OpenWebUI，并且标注来源。

### 场景2：用户问：“发酵罐温度超过42℃的风险是什么？”
1. Dify调用报表引擎查询数据库：**数据库没有存储“风险说明”这类文本**，返回`data_missing=true`；
2. 触发分支，调用qKnow，检索发酵工艺文档、食品安全风险说明；
3. 返回知识库内容，明确标记【知识库参考信息，非实时生产数据】。

## 四、必须处理的边界问题（制造业客户最关心）
### 1. 区分两种“缺失”，逻辑不一样
- **业务数据库里根本不存在这类字段**（如工艺原理）→ 正常交给qKnow补齐，标记为参考知识；
- **数据库有字段，但该时间段数据为空（采集断点）** → AI**不能猜数值**。必须告知：`XX时间段传感器数据缺失，无法统计该指标；以下为参考工艺知识`。
> ❌ 禁止行为：数据库缺一条温度记录，大模型自己估算一个温度值填入报表。这在食品/化工审计是致命问题。

### 2. 来源溯源（对标WorkBuddy审计能力）
每一段回答强制打上来源标签：
- 📊【业务数据库】：量化指标、图表
- 📖【工艺知识库(qKnow)】：SOP、案例、原理
审计日志记录：
- 数据库SQL/查询语句、返回结果
- qKnow检索文档片段、引用文档名称
- Dify工具调用链路、大模型输入输出

### 3. 提示词防护（防止幻觉篡改数据）
Dify系统提示词增加硬性约束：
> 1. 所有量化生产数据只能由数据查询工具返回，不允许模型生成、估算、猜测任何产量、良品率、传感器数值。
> 2. 当数据查询返回空或缺失，必须如实告知用户数据缺失，不可编造数值填补空缺。
> 3. 知识库内容仅作为辅助参考，不能替代数据库内真实生产记录。
> 4. 高危生产建议，必须提示“建议工艺人员现场复核”。

WorkBuddy通常是**统一大模型+工具，不强制区分可信业务库和知识库**；容易出现把AI推理和业务数据混在一起，企业用户分不清真假。
你的架构天然有优势：
1. **可信边界清晰**：量化数据锁死在客户数据库，AI只补知识；制造业客户、审计非常认可；
2. 存储压力低：不用把海量时序生产数据灌进向量库，向量库只放SOP/案例；

## 七、潜在风险

# 先纠正一个关键边界：Dify 是「编排层」，不是「实时引擎」

你的四个功能里，**设备预警、质检、自动化运行都带实时性或定时性**，而 Dify 工作流本质是「HTTP 请求 → 多步编排 → 返回结果」的无状态请求-响应模型，它**不适合常驻订阅数据流、不适合跑 CV 推理、不适合长批处理、定时能力也弱**。正确分工是：

- **Dify 负责**：被触发后的「分析、检索、汇总、写报告、对话应答、工具串联」——这部分放对话界面实现，完全成立；
- **Dify 之外必须补一层触发/实时判定**：实时流阈值、CV 推理、定时调度、事件总线，这层做完判定后**通过 API 调用 Dify 工作流**，Dify 再做智能加工和输出。

## “主要功能在对话界面实现，内部全部打通”的正确落法

1. **对话界面（Open WebUI）是唯一入口，但不是唯一出口**：人主动问走对话；机器自动触发的结果也要回流成对话里的卡片/消息，同时外挂企微/钉钉推送——因为值班人员不会一直盯着聊天窗口。
2. **打通靠「工具注册 + 事件API」，不靠组件互读数据库**：
   - Dify 把 qKnow、报表引擎、CV结果、设备模型、连接器全部注册成工具，工作流里拖拽串联；
   - 外部触发层统一通过 Dify 的 **Workflow 执行API**（API触发模式）调用同一个工作流，做到「人在对话里点」和「系统自动跑」走的是**同一条编排逻辑**，这才是真正的内部打通，而不是两套逻辑。
3. **统一身份是打通的前提**：Open WebUI、Dify、qKnow、报表引擎共用 SSO，Dify 调工具时把当前用户身份和行级权限透传给报表引擎，否则自动触发和对话查询会出现越权读数据。
4. **审计Trace一条链**：对话触发记录 question→工具→结果；自动触发记录 事件源→规则命中→工作流→输出，全部落库，满足食品/化工合规。

## 你方案里现在最容易漏的三件事

- **把实时预警塞进 Dify 工作流**：工作流随会话生命周期结束，流一断预警就停，必须外部常驻规则引擎。
- **让 Dify 直接调模型做质检/预测**：Dify 是编排框架不是推理平台，CV和时序模型要独立服务，Dify 只收结果。
- **只做对话、不做主动推送和调度**：自动化运行的本质是“无人时也在跑”，外部调度器+推送通道这两块不补，“自动化”就只剩“人来问才答”。

3. 写回目标表必须独立写权限，查询不能自动解释为写入；所有运行记录、规则版本、计算证据保存审计日志。

### 2）质量检查 M17
1. **独立质检业务页面**：检测设备、指标模板、检测任务、缺陷明细、人工复核、检测报告；
2. CV图像推理为独立GPU推理服务；业务服务接收图片返回缺陷结果；
3. Dify能力：对话下发质检任务指令；收到检测结果后，调用报表引擎做批次统计，调用qKnow检索工艺缺陷经验，生成质量分析报告；
4. 视觉模型推理、缺陷判定逻辑不在Dify内部实现。

### 3）工作流M11
Dify作为运行时，但是**流程定义、版本管理、画布UI、调度、运行日志、人工复核节点按文档要求实现统一工作流模块页面**。
> 用户既可以在画布拖拽编辑流程；也可以在对话让AI生成工作流定义，保存到统一流程库。
> 业务专用节点（设备采集、预警判定、质检检测、数据分析）本质是调用后端业务能力，Dify只是执行调度。

## 四、权限、安全、审计（V2文档强约束，是对标WorkBuddy的关键，开源组件天然缺失）
1. **统一身份层（自研，不可跳过）**
    Open‑WebUI、Dify、qKnow、报表引擎全部接入同一SSO；工具网关每次调用业务能力透传当前用户身份、工作区、数据权限；
    > 禁止Dify服务账号拥有全量权限，必须继承登录用户的权限；Agent不能绕过页面授权。
2. **工具网关（自研，对标V2 M02/M12）**
    统一做：权限校验、参数Schema校验、限流、防重复调用、副作用确认（写数据库、发布预警需要确认）、审计日志记录每一次tool_call；
    Dify所有工具调用，**不直接调用下游服务，全部经过工具网关中转**。
3. **全链路审计**
    无论来自页面操作还是AI对话，全部落审计日志：操作人、能力ID、入参、返回结果、资源版本、来源；满足食品化工合规。
4. **风险约束**
    - 高危动作（写回生产表、修改预警规则）需要独立确认策略；
    - 量化生产指标只能来自数据库；qKnow内容标记为参考知识，不能作为实测数据；
    - 模型不可用时，普通配置页面依旧可用，AI功能展示“依赖模型不可用”，不整个系统雪崩。

## 六、需要规避的典型坑（对比V2文档踩坑点）
1. ❌坑：直接把Open‑WebUI聊天页作为系统首页；
    ✅正确：登录后是业务首页概览；AI工作台只是一级业务域之一。
2. ❌坑：Dify直接操作数据库，直接运行CV推理、实时预警循环；
    ✅正确：Dify只编排；所有IO、业务计算、推理交给Python业务服务层，通过工具网关调用。
3. ❌坑：对话生成的大屏、预警配置只保存在聊天会话里，业务页面看不到；
    ✅正确：全部存入统一资源库，带版本，脱离对话可管理。
4. ❌坑：Dify/qKnow/Open‑WebUI各自一套账号权限；
    ✅正确：全部接入统一SSO，工具网关做权限拦截。
5. ❌坑：数据库缺数据，让大模型编造数值填补报表；
    ✅正确：返回数据缺失，qKnow只补充参考知识，来源明确标记。

## 七、和WorkBuddy的差异化（基于这套架构）
1. WorkBuddy偏向通用办公Agent；本平台**强工业业务底座**：独立预警、质检、时序数据源、报表大屏业务模块，不是纯聊天Agent外壳。
2. 严格区分**可信业务数据库（事实）**与**qKnow知识图谱（参考推理）**，数据来源可审计，适配食品化工制造业合规。
3. 同一业务能力：表单配置 / AI对话调用 / API调用，三套入口完全复用，不是两套割裂系统。
